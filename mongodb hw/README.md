# 2. Модель данных

Используются две основные коллекции:

- `products` — каталог товаров;
- `orders` — история заказов.

## 2.1. Products

Пример документа:

```javascript
{
    _id: "A",
    name: "Футболка",
    category: "clothes",
    price: NumberDecimal("100.00"),
    variants: [
        {
            size: "L",
            stock: NumberInt(0)
        },
        {
            size: "M",
            stock: NumberInt(10)
        }
    ]
}
```

Размеры и остатки представлены массивом `variants`, поскольку они являются частью одного товара и обычно обрабатываются вместе с ним.

Для коллекции установлен `$jsonSchema` validator в режиме:

```text
validationLevel = strict
validationAction = error
```

Он проверяет:

- наличие обязательных полей;
- строковый тип `_id`, `name`, `category`;
- тип `Decimal128` и неотрицательное значение `price`;
- структуру массива `variants`;
- строковый `size`;
- целочисленный и неотрицательный `stock`.

Проверка показала:

- корректный документ принимается;
- строковое значение цены отклоняется;
- отрицательный остаток отклоняется.

---

## 2.2. Orders

Пример заказа:

```javascript
{
    _id: "purchase-001",
    userId: 2500,
    createdAt: ISODate(...),
    status: "created",
    items: [
        {
            sku: "A",
            size: "M",
            qty: 2,
            price: NumberDecimal("100.00")
        }
    ]
}
```

### Почему позиции встроены в заказ?

Позиции `items` являются частью конкретного заказа и не имеют самостоятельного жизненного цикла.

Обычно заказ читается вместе со всеми его позициями, поэтому embedding позволяет получить его одной операцией без дополнительных соединений.

При этом каждый заказ пользователя хранится отдельным документом, потому что история может расти независимо и к ней применяются сортировка, фильтрация и ограничение количества результатов.

### Что означает `items.price`?

`items.price` — это цена единицы товара **на момент совершения покупки**.

Это исторический факт.

Текущая цена в `products.price` может измениться, но уже созданные заказы и рассчитанная по ним историческая выручка изменяться не должны.

# 3. Поиск товаров

Поиск выполняется по:

- категории;
- размеру;
- достаточному остатку.

Для массива `variants` используется `$elemMatch`:

```javascript
variants: {
    $elemMatch: {
        size: size,
        stock: { $gte: qty }
    }
}
```

Это принципиально важно.

Например:

```javascript
variants: [
    { size: "L", stock: 0 },
    { size: "M", stock: 10 }
]
```

Для запроса `size=L, qty=2` товар не должен подходить.

Без `$elemMatch` MongoDB могла бы найти `size=L` в одном элементе массива, а `stock >= 2` — в другом.

`$elemMatch` требует, чтобы оба условия выполнялись для **одного и того же элемента массива**.

Результаты сортируются по:

```javascript
{ _id: 1 }
```

# 4. История заказов

История фильтруется по:

```text
userId
status
```

и сортируется:

```javascript
{
    createdAt: -1,
    _id: 1
}
```

Затем применяется:

```javascript
limit(20)
```

Основной порядок — самые новые заказы первыми.

`_id ASC` используется как дополнительный критерий при одинаковом `createdAt`, чтобы порядок выдачи был детерминированным.

# 5. Отчёт о продажах

Отчёт строится средствами MongoDB Aggregation Framework.

Учитываются только заказы:

```text
status = paid
```

за период:

```text
[from, to)
```

То есть начало интервала включается, а конец — нет.

Pipeline состоит из следующих основных этапов:

```text
$match
↓
$unwind
↓
$group
↓
$lookup
↓
$unwind
↓
$project
↓
$sort
↓
$limit
```

## Расчёт количества

Для товара:

\[
qty = \sum_i qty_i
\]

## Расчёт выручки

\[
revenue = \sum_i qty_i \cdot price_i
\]

При расчёте используется именно:

```text
items.price
```

а не текущий `products.price`.

### Пример товара A

Товар A был продан:

```text
2 × 100 = 200
1 × 120 = 120
```

Следовательно:

```text
qty = 2 + 1 = 3
revenue = 200 + 120 = 320
```

Итог:

```text
A — Футболка — qty=3 — revenue=320.00
```

После изменения текущей цены товара A на `999.00` историческая выручка осталась `320.00`, поскольку стоимость позиции фиксируется в заказе.

Фактический top-5:

| SKU | Название | Количество | Выручка |
|---|---|---:|---:|
| A | Футболка | 3 | 320.00 |
| B | Рубашка | 4 | 320.00 |
| C | Толстовка | 3 | 270.00 |
| D | Ремень | 2 | 240.00 |
| E | Сумка | 1 | 200.00 |

# 6. Индекс и план выполнения

Для истории используется запрос:

```javascript
find({
    userId: 2500,
    status: "paid"
})
.sort({
    createdAt: -1,
    _id: 1
})
.limit(20)
```

Создан составной индекс:

```javascript
{
    userId: 1,
    status: 1,
    createdAt: -1,
    _id: 1
}
```

Он построен в соответствии с принципом ESR:

```text
Equality → Equality → Sort
```

`userId` и `status` используются для проверки равенства, а `createdAt` и `_id` обеспечивают требуемый порядок.

`hint` не использовался.

## Результаты explain("executionStats")

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | Да |
| После индекса | 20 | 20 | 20 | Нет |

До создания индекса MongoDB выполняла `COLLSCAN`, просматривая все 10 000 документов, после чего выполняла отдельную сортировку.

После создания индекса используется `IXSCAN`.

MongoDB просмотрела только 20 ключей индекса и 20 документов.

Отдельная стадия `SORT` исчезла, поскольку порядок документов уже соответствует порядку составного индекса.

При этом состав и порядок результата до и после создания индекса не изменились.

## Издержки индекса

Индекс:

- занимает дополнительное место на диске и в памяти;
- должен обновляться при `insert`, `update` и `delete`;
- увеличивает стоимость операций записи.

Поэтому создание индекса является компромиссом между скоростью чтения и стоимостью хранения и изменения данных.

# 7. Оформление заказа и транзакция

Покупка выполняется одной многодокументной транзакцией.

Транзакция использует:

```text
readConcern: snapshot
readPreference: primary
writeConcern:
    w: majority
    j: true
```

В рамках одной транзакции выполняются:

```text
проверка operationId
↓
списание первого товара
↓
списание второго товара
↓
создание Order
↓
commit
```

Если на любом этапе возникает ошибка:

```text
throw
↓
abortTransaction()
```

---

## 7.1. Атомарное списание остатка

Проверка наличия товара и списание объединены в одну операцию `updateOne`.

Условие содержит:

```text
sku
size
stock >= qty
```

а обновление:

```javascript
$inc: {
    "variants.$.stock": -qty
}
```

Поэтому между отдельной проверкой остатка и его изменением нет окна для изменения состояния другим запросом.

Если:

```text
modifiedCount != 1
```

операция завершается:

```text
ITEM_UNAVAILABLE
```

Один код используется для случаев:

- SKU не существует;
- размер не существует;
- остатка недостаточно.

---

# 8. Rollback

В контрольном опыте первый товар успешно изменяется:

```text
A:
matched = 1
modified = 1
```

После этого попытка списания второго товара завершается неудачно:

```text
B:
matched = 0
modified = 0
```

Возникает:

```text
ITEM_UNAVAILABLE
```

и транзакция выполняет abort.

Несмотря на то, что первое обновление действительно произошло внутри транзакции, после abort состояние полностью восстанавливается:

```text
A/M stock = 10
B/L stock = 5
orderCount = 0
```

Таким образом, промежуточное изменение первого товара не становится видимым как завершённый результат покупки.

---

# 9. Успешная покупка

Для операции:

```text
operationId = purchase-001
```

успешно списаны:

```text
A/M: 10 → 8
B/L: 5 → 4
```

Создан ровно один заказ:

```javascript
{
    _id: "purchase-001",
    userId: 2500,
    status: "created",
    items: [
        {
            sku: "A",
            size: "M",
            qty: 2,
            price: 100.00
        },
        {
            sku: "B",
            size: "L",
            qty: 1,
            price: 80.00
        }
    ]
}
```

Проверены BSON-типы:

- `userId` — integer;
- `qty` — integer;
- `price` — Decimal128;
- `createdAt` — BSON Date.

# 10. Повтор запроса и идемпотентность

`operationId` используется как `_id` заказа.

Перед новой покупкой выполняется поиск существующего заказа.

Если заказ с таким `operationId` уже существует и совпадают:

```text
userId
items[].sku
items[].size
items[].qty
```

возвращается уже сохранённый `Order`.

Новые списания не выполняются.

При проверке повторного запроса текущая цена товара в каталоге была изменена, а порядок ключей JS-объекта отличался.

Тем не менее был корректно возвращён первоначальный заказ, а остатки не изменились.

Если использовать тот же `operationId`, но изменить бизнес-параметры, например `qty`, операция завершается:

```text
REQUEST_CONFLICT
```

---

## Atomicity и idempotency — разные свойства

### Atomicity

Транзакция гарантирует:

> либо выполнятся все изменения одной покупки, либо не выполнится ни одно.

Например:

```text
списание A
+
списание B
+
создание заказа
```

либо фиксируются вместе, либо полностью отменяются.

### Idempotency

`operationId` решает другую проблему:

> один и тот же подтверждённый бизнес-запрос не должен выполнить покупку повторно.

Таким образом:

```text
transaction → защита целостности одной попытки;

operationId → защита от повторного выполнения бизнес-операции.
```

# 12. Смена primary

До переключения роли replica set были:

```text
m1 — PRIMARY
m2 — SECONDARY
m3 — SECONDARY
```

Перед переключением была выполнена запись с:

```javascript
{
    w: "majority",
    j: true
}
```

и получено подтверждение записи.

После `stepDown` новым primary стал:

```text
m3
```

Роли:

```text
m1 — SECONDARY
m2 — SECONDARY
m3 — PRIMARY
```

При этом использовался **тот же экземпляр MongoDB-клиента**.

После смены primary удалось:

1. прочитать документ, записанный до переключения;
2. выполнить новую majority-запись.

---

## Как клиент находит новый primary?

Клиент подключён не к одному конкретному серверу, а к replica set:

```text
mongodb://m1:27017,m2:27017,m3:27017/...?
replicaSet=hw2rs
```

Драйвер знает топологию replica set и отслеживает состояние его участников.

После смены primary он обнаруживает новый узел с ролью PRIMARY и отправляет дальнейшие операции записи ему.

Поэтому приложение не должно вручную менять адрес с `m1` на `m3`.

---

## Почему majority write не гарантирует мгновенно актуальное чтение с любой secondary?

`w: "majority"` гарантирует необходимый уровень подтверждения записи replica set.

Но secondary-узлы применяют операции асинхронно.

Поэтому конкретная secondary в некоторый момент может ещё не применить самую новую запись.

Гарантии записи и выбор источника чтения — разные настройки.

В данном стенде используется:

```text
readPreference: primary
```

поэтому обычные чтения направляются на текущий primary.

# 13. Шардирование

Дана карта распределения `orders` по shard key:

```javascript
{ userId: 1 }
```

Распределение:

| userId | Shard |
|---|---|
| `< 2000` | A |
| `2000 <= userId < 5000` | B |
| `>= 5000` | A |

## 13.1. История пользователя 2500

Запрос:

```javascript
{
    userId: 2500
}
```

значение `2500` входит в диапазон:

```text
2000 <= userId < 5000
```

Поэтому `mongos` отправит запрос только:

```text
Shard B
```

Это targeted query, поскольку значение shard key известно.

---

## 13.2. Общий отчёт по paid

Запрос:

```javascript
{
    status: "paid"
}
```

не содержит `userId`.

Следовательно `mongos` не может определить нужный диапазон shard key.

Он должен отправить запрос:

```text
Shard A
+
Shard B
```

То есть выполняется scatter-gather.

---

## 13.3. Что изменит индекс `{status: 1}`?

Количество опрашиваемых шардов **не изменится**.

Оба шарда всё равно необходимо опросить, потому что условие не содержит shard key.

Индекс:

```javascript
{ status: 1 }
```

может ускорить поиск документов со значением:

```text
status = paid
```

внутри каждого отдельного шарда.

Но он не изменяет маршрутизацию запроса между шардами.

Маршрутизация определяется shard key и картой chunks.
