## 2. Модель данных

Используются две основные коллекции:

- `products` — каталог товаров;
- `orders` — история заказов.

### 2.1. Products

Пример документа:

```javascript
{
    _id: "A",
    name: "Футболка",
    category: "clothes",
    price: NumberDecimal("100.00"),
    variants: [
        {
            size: "L",
            stock: NumberInt(0)
        },
        {
            size: "M",
            stock: NumberInt(10)
        }
    ]
}
```

Размеры и остатки представлены массивом `variants`, поскольку они являются частью одного товара и обычно обрабатываются вместе с ним.

Для коллекции установлен `$jsonSchema` validator в режиме:

```text
validationLevel = strict
validationAction = error
```

Он проверяет:

- наличие обязательных полей;
- строковый тип `_id`, `name`, `category`;
- тип `Decimal128` и неотрицательное значение `price`;
- структуру массива `variants`;
- строковый `size`;
- целочисленный и неотрицательный `stock`.

Проверка показала:

- корректный документ принимается;
- строковое значение цены отклоняется;
- отрицательный остаток отклоняется.

### 2.2. Orders

Пример заказа:

```javascript
{
    _id: "purchase-001",
    userId: 2500,
    createdAt: ISODate(...),
    status: "created",
    items: [
        {
            sku: "A",
            size: "M",
            qty: 2,
            price: NumberDecimal("100.00")
        }
    ]
}
```

### Почему позиции встроены в заказ?

Позиции `items` являются частью конкретного заказа и не имеют самостоятельного жизненного цикла.

Обычно заказ читается вместе со всеми его позициями, поэтому embedding позволяет получить его одной операцией без дополнительных соединений.

При этом каждый заказ пользователя хранится отдельным документом, потому что история может расти независимо, а к ней применяются фильтрация, сортировка и ограничение количества результатов.

### Что означает `items.price`?

`items.price` — цена единицы товара на момент совершения покупки.

Это исторический факт. Текущая цена в `products.price` может измениться, но уже созданные заказы и рассчитанная по ним историческая выручка изменяться не должны.

## 3. Поиск товаров

Поиск выполняется по категории, размеру и достаточному остатку.

Для массива `variants` используется `$elemMatch`:

```javascript
variants: {
    $elemMatch: {
        size: size,
        stock: { $gte: qty }
    }
}
```

Это важно, потому что размер и достаточный остаток должны относиться к одному и тому же элементу массива.

Например:

```javascript
variants: [
    { size: "L", stock: 0 },
    { size: "M", stock: 10 }
]
```

Для запроса `size=L, qty=2` товар не должен подходить.

Без `$elemMatch` условие по размеру могло бы выполниться на одном элементе массива, а условие по остатку — на другом.

Результаты сортируются по `_id` по возрастанию.

---

## 4. История заказов

История фильтруется по `userId` и `status` и сортируется:

```javascript
{
    createdAt: -1,
    _id: 1
}
```

После этого применяется:

```javascript
limit(20)
```

Основной порядок — самые новые заказы первыми.

`_id ASC` используется как дополнительный критерий при одинаковом `createdAt`, чтобы порядок выдачи был детерминированным.

## 5. Отчёт о продажах

Отчёт строится средствами MongoDB Aggregation Framework.

Учитываются только заказы со статусом `paid` за период:

```text
[from, to)
```

То есть начало интервала включается, а конец — нет.

Pipeline состоит из следующих основных этапов:

```text
$match
↓
$unwind
↓
$group
↓
$lookup
↓
$unwind
↓
$project
↓
$sort
↓
$limit
```

Количество для товара считается как сумма `qty`, а выручка — как сумма произведений количества на цену позиции заказа:

```text
revenue = Σ(qty × items.price)
```

При расчёте используется именно `items.price`, а не текущий `products.price`.

### Пример товара A

Товар A был продан:

```text
2 × 100 = 200
1 × 120 = 120
```

Следовательно:

```text
qty = 3
revenue = 320
```

Итог:

```text
A — Футболка — qty=3 — revenue=320.00
```

Фактический top-5:

| SKU | Название | Количество | Выручка |
|---|---|---:|---:|
| A | Футболка | 3 | 320.00 |
| B | Рубашка | 4 | 320.00 |
| C | Толстовка | 3 | 270.00 |
| D | Ремень | 2 | 240.00 |
| E | Сумка | 1 | 200.00 |

После изменения текущей цены товара A на `999.00` историческая выручка осталась `320.00`, поскольку стоимость позиции фиксируется в заказе на момент покупки.

Также проверены пустой период и корректная обработка границ `[from, to)`.

## 6. Индекс и план выполнения

Для истории используется запрос:

```javascript
find({
    userId: 2500,
    status: "paid"
})
.sort({
    createdAt: -1,
    _id: 1
})
.limit(20)
```

Создан составной индекс:

```javascript
{
    userId: 1,
    status: 1,
    createdAt: -1,
    _id: 1
}
```

Первые два поля используются для фильтрации по равенству, а `createdAt` и `_id` соответствуют сортировке.

`hint` не использовался.

### Результаты `explain("executionStats")`

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | Да |
| После индекса | 20 | 20 | 20 | Нет |

До создания индекса MongoDB выполняла `COLLSCAN`, просматривая все 10 000 документов, после чего выполняла отдельную сортировку.

После создания индекса используется `IXSCAN`.

MongoDB просмотрела только 20 ключей индекса и 20 документов.

Отдельная стадия `SORT` исчезла, поскольку порядок документов уже соответствует порядку составного индекса.

При этом состав и порядок результата до и после создания индекса не изменились.

### Издержки индекса

Индекс занимает дополнительное место на диске и в памяти и должен обновляться при `insert`, `update` и `delete`.

Таким образом, индекс ускоряет чтение ценой дополнительных затрат на хранение и изменение данных.

## 7. Оформление заказа и транзакция

Покупка выполняется одной многодокументной транзакцией.

Транзакция использует:

```text
readConcern: snapshot
readPreference: primary

writeConcern:
    w: majority
    j: true
```

В рамках одной транзакции выполняются:

```text
проверка operationId
↓
списание первого товара
↓
списание второго товара
↓
создание Order
↓
commit
```

Если на любом этапе возникает ошибка, выполняется `abortTransaction()`.

### Атомарное списание остатка

Проверка наличия товара и списание объединены в одну операцию `updateOne`.

Условие содержит SKU, размер и проверку:

```text
stock >= qty
```

Обновление выполняется через:

```javascript
$inc: {
    "variants.$.stock": -qty
}
```

Таким образом, проверка остатка и его уменьшение выполняются одной атомарной операцией над документом товара.

Если `modifiedCount != 1`, операция завершается ошибкой:

```text
ITEM_UNAVAILABLE
```

Один код используется для случаев:

- SKU не существует;
- размер не существует;
- остатка недостаточно.

## 8. Rollback

В контрольном опыте первый товар успешно изменяется:

```text
A:
matched = 1
modified = 1
```

После этого попытка списания второго товара завершается неудачно:

```text
B:
matched = 0
modified = 0
```

Возникает `ITEM_UNAVAILABLE`, после чего транзакция выполняет abort.

Несмотря на то, что первое обновление действительно произошло внутри транзакции, после abort состояние полностью восстанавливается:

```text
A/M stock = 10
B/L stock = 5
orderCount = 0
```

Таким образом, промежуточное изменение первого товара не сохраняется после неуспешного завершения покупки.

## 9. Успешная покупка

Для операции:

```text
operationId = purchase-001
```

успешно списаны:

```text
A/M: 10 → 8
B/L: 5 → 4
```

Создан ровно один заказ:

```javascript
{
    _id: "purchase-001",
    userId: 2500,
    status: "created",
    items: [
        {
            sku: "A",
            size: "M",
            qty: 2,
            price: NumberDecimal("100.00")
        },
        {
            sku: "B",
            size: "L",
            qty: 1,
            price: NumberDecimal("80.00")
        }
    ]
}
```

Проверены BSON-типы:

- `userId` — integer;
- `qty` — integer;
- `price` — Decimal128;
- `createdAt` — BSON Date.

## 10. Повтор запроса и идемпотентность

`operationId` используется как `_id` заказа.

Перед новой покупкой выполняется поиск существующего заказа.

Если заказ с таким `operationId` уже существует и совпадают:

```text
userId
items[].sku
items[].size
items[].qty
```

возвращается уже сохранённый `Order`.

Новые списания не выполняются.

При проверке повторного запроса текущая цена товара в каталоге была изменена, а порядок ключей объекта отличался. Тем не менее был корректно возвращён первоначальный заказ, а остатки не изменились.

Если использовать тот же `operationId`, но изменить бизнес-параметры, например `qty`, операция завершается:

```text
REQUEST_CONFLICT
```

### Atomicity и idempotency

Транзакция обеспечивает атомарность:

> либо списываются оба товара и создаётся заказ, либо все изменения покупки откатываются.

`operationId` решает другую задачу:

> одна уже подтверждённая бизнес-операция не должна выполниться повторно.

То есть:

```text
transaction → атомарность одной попытки;
operationId → защита от повторного выполнения покупки.
```

## 11. Счётчики транзакций

Для успешной покупки и сценария rollback были получены отдельные снимки `serverStatus().transactions` до и после выполнения операции.

Численные разности счётчиков:

| Сценарий | Δ totalStarted | Δ totalCommitted | Δ totalAborted |
|---|---:|---:|---:|
| Успешная покупка | 1 | 1 | 0 |
| Откат после первого успешного списания | 1 | 0 | 1 |

Для успешной покупки увеличились счётчики запущенных и зафиксированных транзакций:

```text
Δ totalStarted   = 1
Δ totalCommitted = 1
Δ totalAborted   = 0
```

Для сценария rollback:

```text
Δ totalStarted   = 1
Δ totalCommitted = 0
Δ totalAborted   = 1
```

Это соответствует фактическому поведению сценариев: успешная покупка завершилась `commit`, а покупка с нехваткой второго товара — `abort`.

Счётчики являются дополнительным подтверждением поведения транзакции. Основная атомарность также проверяется по состоянию товаров и отсутствию заказа после rollback.

Полные снимки `before` и `after`, сведения о процессе и значения `delta` сохранены в:

```text
results/results.json
```

## 12. Смена primary

В сохранённом итоговом прогоне до переключения роли replica set были следующими:

```text
m1 — SECONDARY
m2 — PRIMARY
m3 — SECONDARY
```

Перед переключением была выполнена контрольная запись с:

```javascript
{
    w: "majority",
    j: true
}
```

Запись была успешно подтверждена.

После `stepDown` новым primary стал `m1`.

Роли после выборов:

```text
m1 — PRIMARY
m2 — SECONDARY
m3 — SECONDARY
```

Таким образом, в сохранённом прогоне произошло переключение:

```text
m2 → m1
```

При этом использовался тот же экземпляр MongoDB-клиента.

После смены primary удалось:

1. прочитать документ, записанный до переключения;
2. выполнить новую majority-запись;
3. подтвердить наличие обоих документов.

### Как клиент находит новый primary?

Клиент подключён не к одному конкретному серверу, а ко всему replica set:

```text
mongodb://m1:27017,m2:27017,m3:27017/...?
replicaSet=hw2rs
```

Клиент отслеживает топологию replica set и состояние его участников.

После выборов он обнаруживает новый узел с ролью PRIMARY и направляет последующие операции записи ему.

Поэтому приложению не требуется вручную менять адрес подключения с `m2` на `m1`.

### Почему majority write не гарантирует немедленно актуальное чтение с любой secondary?

`w: "majority"` задаёт условие подтверждения записи replica set.

При этом применение изменений отдельными secondary и выбор источника чтения являются отдельными механизмами.

Поэтому конкретная secondary не обязана в любой момент использоваться как источник самого нового состояния только из-за того, что запись ранее получила majority acknowledgement.

В данном стенде используется:

```text
readPreference: primary
```

поэтому обычные чтения направляются текущему primary.

## 13. Шардирование

Коллекция `orders` распределена по shard key:

```javascript
{ userId: 1 }
```

Распределение:

| userId | Shard |
|---|---|
| `< 2000` | A |
| `2000 <= userId < 5000` | B |
| `>= 5000` | A |

### 13.1. История пользователя 2500

Запрос:

```javascript
{
    userId: 2500
}
```

Значение `2500` входит в диапазон:

```text
2000 <= userId < 5000
```

Поэтому `mongos` отправит запрос только на:

```text
Shard B
```

Это targeted query, поскольку значение shard key известно.

### 13.2. Общий отчёт по `paid`

Запрос:

```javascript
{
    status: "paid"
}
```

не содержит `userId`.

Следовательно, `mongos` не может определить единственный нужный диапазон shard key.

Он должен отправить запрос на:

```text
Shard A
+
Shard B
```

То есть выполняется scatter-gather.

### 13.3. Индекс `{status: 1}`

После создания индекса:

```javascript
{ status: 1 }
```

количество опрашиваемых шардов не изменится.

Оба шарда всё равно необходимо опросить, поскольку условие запроса не содержит shard key.

Индекс может ускорить поиск документов со статусом `paid` внутри каждого отдельного шарда, но не изменяет маршрутизацию запроса между шардами.
