# Домашняя работа №3 — Apache Cassandra

## 1. Цель работы и описание сервиса

Цель работы — реализовать хранение и чтение журнала пользовательских действий в распределённой СУБД Apache Cassandra, исследовать уровни консистентности ONE и QUORUM, влияние сжатия LZ4, Bloom-фильтры, TTL, компакцию и синхронизацию реплик (`nodetool repair`).

Сервис аудита фиксирует три типа действий: `login` (вход), `purchase` (покупка), `view` (просмотр). Основной запрос — получить последние события конкретного пользователя в обратном хронологическом порядке.

Стенд запускается в Docker Compose: Cassandra 5.0.4, три узла `c1`, `c2`, `c3`, keyspace `hw3` с `replication factor = 3`. Рабочие функции реализованы в `solution.py`; проверки выполняются программой `lab.py`. Служебные файлы стенда и контрольные данные не изменялись.

## 2. Модель данных и создание таблиц

Созданы две таблицы с одинаковыми колонками:

| Поле | Тип | Назначение |
|---|---|---|
| `user_id` | `int` | Идентификатор пользователя и partition key |
| `event_time` | `timestamp` | Время события и clustering key |
| `event_type` | `text` | Тип действия: `login`, `purchase` или `view` |
| `payload` | `text` | Дополнительные данные события в формате JSON |

Первичный ключ: `PRIMARY KEY (user_id, event_time)`. Порядок кластеризации: `CLUSTERING ORDER BY (event_time DESC)`. Для `user_actions` используется `LZ4Compressor`, для `user_actions_none` сжатие отключено (`compression = {'enabled': 'false'}`). Вторая таблица нужна исключительно для сопоставления размеров SSTable.

**Почему partition key — `user_id`?** Основной запрос приложения — лента конкретного пользователя. Такой ключ позволяет адресовать его партицию без сканирования данных всех пользователей. При этом в реальной системе нужно следить за размером партиций: у очень активного пользователя история может стать слишком большой. Возможное масштабирование — разбивка по временному периоду, например `(user_id, month_bucket)`, при соответствующей переработке запросов.

**Почему `event_time DESC`?** События внутри партиции упорядочены от новых к старым. Получение последних `LIMIT N` записей не требует дополнительной сортировки в Python.

**Коллизия `event_time`.** Если два события одного пользователя имеют одинаковое время, их полный первичный ключ совпадает. Cassandra не создаст две независимые строки, а применит обновление ячеек по правилам разрешения конфликтов по timestamp записи. Для аудита это опасно потерей самостоятельных событий. Решение — включить уникальный `event_id` в ключ, например `PRIMARY KEY (user_id, event_time, event_id)` с `event_id timeuuid` или UUID; сортировку по времени сохранить. Тогда даже события с одинаковым `event_time` смогут храниться отдельно.

**Проверка:** `docker compose run --rm lab data` — 16/16 проверок. Вставлены 20 контрольных событий пользователя `1001`; выборка последних пяти идёт от события `i=19` (`2026-01-01 00:19:00`, `purchase`) до `i=15`.

## 3. Вставка и чтение через PreparedStatement

В `insert_events()` используется параметризованный запрос `INSERT ... VALUES (?, ?, ?, ?)`, подготовленный один раз через `session.prepare()`. Затем для каждого события выполняются `prepared.bind((user_id, event_time, event_type, payload))` и `session.execute(bound)`.

Данные генерируются детерминированно: `BASE_EVENT_TIME = 2026-01-01 00:00:00` (UTC без `tzinfo`), каждое следующее событие на одну минуту позже, типы циклично сменяются `login` → `purchase` → `view`, поле `payload` содержит `{"seq": i}`. Таблица задаётся параметром функции; в сценарии `bulk` одинаковые 10 000 записей попадают в обе таблицы.

`read_last()` использует параметризованный `SELECT ... WHERE user_id = ? LIMIT ?`. Порядок `DESC` обеспечивается схемой таблицы. Уровень консистентности устанавливается **на связанном запросе** (`bound.consistency_level = consistency`), а не глобально для сессии.

**Зачем PreparedStatement?** Подготовка запроса отделяет его структуру от значений, позволяет повторно использовать один план/подготовленное представление при множественных записях, уменьшает повторный разбор запроса и обеспечивает корректную передачу параметров. Имена таблиц, в отличие от значений, не подставляются через `?`, поэтому строковый параметр `table` должен поступать из доверенного набора имён.

### Измерение bulk

| Что вставлено | Количество | Общее время | Среднее время на запись |
|---|---:|---:|---:|
| События пользователя `1001` (`login`, `purchase`, `view`) | 10 000 | 5,702 с | 0,5702 мс |

Расчёт: `5,702 / 10 000 = 0,0005702 с = 0,5702 мс`. Указано время вставки из финального сценария `all`; это время последовательного вызова операций в данном тестовом окружении, а не универсальный бенчмарк Cassandra.

**Проверка:** `docker compose run --rm lab bulk` — 5/5 проверок. Подтверждены 10 000 событий в каждой таблице и правильный порядок чтения.

## 4. Консистентность ONE и QUORUM

Для keyspace `hw3` коэффициент репликации `N = 3`. На уровне `ONE` операция считается подтверждённой после ответа одной реплики, на `QUORUM` — после ответа большинства, то есть двух реплик. Уровень консистентности определяет требуемое число подтверждений; запись может отправляться и другим репликам асинхронно относительно подтверждения клиенту.

Эксперимент: 1000 записей отдельно для `user_id = 2001` (`ONE`) и `user_id = 2002` (`QUORUM`), затем чтение последних 20 событий. Для каждой операции выполнено шесть запусков: один прогревочный, пять измеряемых; ниже приведены медианы, предоставленные `results/results.json`.

| Уровень консистентности | Запись 1000 событий, мс | Чтение 20 событий, мс |
|---|---:|---:|
| `ONE` | 919 | 3 |
| `QUORUM` | 720 | 3 |

Сырые измерения после прогрева (в секундах):

- Запись ONE: `0.505, 0.604, 0.919, 0.927, 1.495`.
- Запись QUORUM: `0.676, 0.687, 0.720, 0.788, 1.326`.
- Чтение ONE: `0.003, 0.003, 0.003, 0.004, 0.004`.
- Чтение QUORUM: `0.002, 0.002, 0.003, 0.003, 0.003`.

**Формула `W + R > N`.** Здесь `W` — число реплик, подтверждающих запись, `R` — число реплик, участвующих в чтении, `N` — число реплик для данного ключа. Для `ONE + ONE`: `1 + 1 = 2 ≤ 3`; пересечение необязательно, поэтому чтение потенциально может вернуть старое состояние. Для `QUORUM + QUORUM`: `2 + 2 = 4 > 3`; множества реплик пересекаются, и успешно подтверждённая запись должна быть видна последующему чтению при отсутствии конкурирующих изменений и с учётом модели разрешения конфликтов Cassandra. Это не эквивалентно полноценным ACID-транзакциям.

**Интерпретация времени.** В данном прогоне запись с QUORUM оказалась быстрее, чем с ONE (720 мс против 919 мс). Это не означает, что QUORUM всегда быстрее: задержки зависят от состояния узлов, прогрева, фоновой активности, Docker и вариативности небольшого эксперимента. Медианы чтения равны с точностью до миллисекунды. Для устойчивого вывода о производительности потребовалась бы серия независимых прогонов в контролируемых условиях.

**Выбор для ленты аудита.** Для критичных событий, особенно финансовых, выбрал(а) бы `QUORUM` для записи и чтения, поскольку важно видеть подтверждённые события, даже ценой дополнительных требований к доступности реплик. Для менее критичной ленты просмотров, где допустима временная устарелость данных, `ONE` может снизить требования к числу отвечающих реплик.

**Проверка:** `docker compose run --rm lab consistency` — 4/4 проверки.

## 5. Сжатие SSTable

После заполнения обеих таблиц одинаковыми данными выполнена команда `bash ops.sh tablestats`. Скрипт предварительно выполняет `nodetool flush hw3`: это необходимо, чтобы сравнивать данные, записанные в SSTable на диске, а не находящиеся только в memtable.

| Показатель | `user_actions` (LZ4) | `user_actions_none` (без сжатия) |
|---|---:|---:|
| Space used (total), байт | 153 995 | 389 878 |
| SSTable count | 1 | 1 |
| SSTable Compression Ratio | 0.38595 | -1.00000 |

Разница в занимаемом месте: `389 878 - 153 995 = 235 883 байта`. Экономия относительно таблицы без сжатия: `235 883 / 389 878 × 100% ≈ 60,5%`. Таблица с LZ4 заняла примерно в `2,53` раза меньше места. Значение `-1.00000` для таблицы без сжатия — служебное значение метрики, а не физически отрицательное сжатие.

**Компромисс.** LZ4 расходует дополнительные ресурсы CPU на сжатие при записи SSTable и распаковку при чтении, но уменьшает объём хранения и потенциально объём дискового ввода-вывода. Для большого журнала однотипных событий это выгодно: в данном эксперименте экономия места значительна. Результат справедлив для измеренного набора данных и не гарантирует ту же степень сжатия для любого содержимого.

Артефакты: `results/tablestats.txt`, `results/tablestats_plain.txt`.

## 6. Bloom-фильтр

В `results/tablestats.txt` для `hw3.user_actions` получены значения:

| Показатель | Значение |
|---|---:|
| Bloom filter false positives | 0 |
| Bloom filter false ratio | 0.00000 |

Bloom-фильтр — вероятностная структура, позволяющая быстро проверить, *может ли* нужный ключ находиться в конкретной SSTable. Ответ «точно отсутствует» позволяет пропустить поиск соответствующего ключа на диске в этой SSTable. Ответ «возможно присутствует» требует дальнейшей проверки. Ложноположительные результаты возможны, ложноотрицательных для корректного фильтра нет.

В данном измерении ложноположительные срабатывания не зарегистрированы. Нулевое значение не означает нулевую теоретическую вероятность ошибки: это наблюдение за конкретный период. Bloom-фильтр особенно полезен при поиске отсутствующих данных и наличии множества SSTable; он менее заметен, если необходимые данные и так находятся в известных/закешированных структурах.

## 7. Repair и согласование реплик

Выполнена команда:

```bash
bash ops.sh repair
```

Результат сохранён в `results/repair.txt`. Проверка `metrics` подтвердила, что файл непустой и операция прошла без ошибок.

**Anti-entropy repair** — фоновая относительно клиентского чтения процедура сравнения и согласования данных между репликами. `nodetool repair` помогает устранить расхождения, возникшие из-за временной недоступности узлов и пропущенных изменений.

**Зачем запускать регулярно?** Без repair отдельные реплики могут длительно хранить разные версии данных, а после истечения периода хранения tombstones и некорректной синхронизации появляется риск восстановления ранее удалённых записей («zombie data»). Repair особенно важен после длительных сбоев и до того, как удалённые данные перестанут быть защищены tombstones.

**Сравнение механизмов:**

| Механизм | Когда помогает | Ограничение |
|---|---|---|
| `nodetool repair` | Плановое сравнение и согласование реплик | Требует ресурсов; запускать осознанно |
| Read repair | Исправление расхождений, выявленных при чтении | Затрагивает только прочитанные данные и зависит от поведения версии/настроек |
| Hinted handoff | Доставка пропущенных мутаций после короткого простоя узла | Хинты хранятся ограниченное время, не заменяют регулярный repair |

## 8. TTL и компакция

Для таблицы `user_actions` настроены:

```sql
ALTER TABLE user_actions
WITH compaction = {
    'class': 'TimeWindowCompactionStrategy',
    'compaction_window_unit': 'DAYS',
    'compaction_window_size': '1'
}
AND default_time_to_live = 2592000;
```

`2592000` секунд = 30 дней. Параметры подтверждены проверкой `system_schema.tables`: класс `org.apache.cassandra.db.compaction.TimeWindowCompactionStrategy`, размер окна `1`, единица окна `DAYS`.

**Эксперимент TTL.** Проверочный сценарий записал 5 событий пользователя `3001` с явным TTL 5 секунд (переопределяющим TTL по умолчанию): до истечения срока было видно 5 строк, после — 0. Это подтверждает логическое истечение данных, но не их немедленное физическое удаление с диска.

**Почему TWCS лучше STCS для журнала событий?** Данные журнала поступают преимущественно по времени и со временем устаревают. TWCS группирует SSTable по временным окнам и позволяет освобождать пространство целыми истёкшими SSTable, когда это безопасно. STCS в первую очередь группирует SSTable по размеру, может смешивать данные разных временных периодов и затруднять своевременное освобождение пространства. В рамках активного окна TWCS сама может применять размерное объединение SSTable; корректная работа лучше достигается при приблизительно последовательных временных записях и согласованных сроках TTL.

**TTL и `gc_grace_seconds`.** По истечении TTL строка становится логически удалённой, а информация об удалении (tombstone) предотвращает возвращение старых данных с отстающих реплик. `gc_grace_seconds` определяет защитный период перед возможной физической очисткой tombstones; само истечение периода не удаляет данные немедленно — нужна подходящая компакция и выполнение условий безопасности. Нельзя сокращать этот параметр без учёта периода недоступности реплик и регулярности repair.

**Почему TTL предпочтительнее массового `DELETE`?** TTL позволяет задавать срок хранения при записи и автоматически завершать жизненный цикл данных без отдельного сканирования и многочисленных команд удаления. При этом TTL **тоже приводит к tombstones**: преимущество заключается в предсказуемой политике хранения и возможности эффективной компакции, а не в полном отсутствии tombstones.

### Трассировка истёкших данных (дополнительный ручной шаг)

В задании требуется включить трассировку `TRACING ON` в `cqlsh` и прочитать партицию с истёкшими событиями. Команды:

```bash

```

```sql
TRACING ON;
SELECT * FROM hw3.user_actions WHERE user_id = 3001;
TRACING OFF;
```

При чтении проверяется отсутствие возвращаемых строк и, если соответствующие tombstones ещё участвуют в операции чтения, наличие записей об их обработке в трассе. **Этот ручной шаг следует выполнить отдельно и зафиксировать фактический вывод или скриншот.** Отсутствие упоминания tombstone в конкретной трассе само по себе не доказывает некорректную работу TTL: после компакции SSTable могла быть очищена или чтение могло не затронуть её.
